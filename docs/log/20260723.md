# 2. 프로젝트의 현재 위치

현재 프로젝트는 단순히 메뉴 화면만 구현하는 단계에서 벗어나 다음 구조를 갖추기 시작했다.

```text
입력값
  ↓
Normalizer
  ↓
Validator
  ↓
PersonCreate
  ↓
Service
  ↓
Repository
  ↓
SQLite
```

아직 `Service`와 `Repository`의 사람 등록 기능은 완성되지 않았지만, 그 앞단에 필요한 데이터 처리 규칙이 상당히 구체적으로 만들어졌다.

현재 소스 구조에는 다음 패키지가 확인된다.

```text
config
database
model
normalizer
ui
validator
```

이는 처음의 단순한 `Main → Menu` 구조에서 실제 애플리케이션 계층 구조로 발전하고 있다는 의미다.

# 3. 이번 개발에서 가장 잘된 부분

## 3.1 Normalizer와 Validator의 책임이 분리되었다

현재 설계에서 가장 중요한 발전이다.

`PersonNormalizer`는 다음과 같은 변환을 담당한다.

```text
이름의 공백 제거
전화번호에서 숫자만 추출
은행 이름의 공백 제거
계좌번호에서 숫자만 추출
주소의 연속된 공백 정리
```

예를 들어:

```text
010-1234-1234
        ↓
01012341234
```

이 작업은 검증이 아니라 표준화다.

그 이후 `PersonValidator`가 다음을 검사한다.

```text
필수 입력 여부
글자 수
문자 또는 숫자 구성 여부
허용된 성별 코드
허용된 은행명
전화번호 시작 번호
```

이제 각각의 클래스가 무엇을 해야 하는지가 명확해졌다.

```text
Normalizer
→ 값을 바꾼다.

Validator
→ 값이 규칙에 맞는지 검사한다.
```

이 구분은 이후 공사, 업체, 계약, 급여 기능을 만들 때 그대로 재사용할 수 있다.

---

## 3.2 CommonValidator를 분리한 판단이 적절하다

이번 커밋에서 `CommonValidator`가 새로 작성되었다.

현재 들어 있는 공통 검증 기능은 다음과 같다.

```java
requireText()
validateLength()
validateLettersOnly()
validateDigitsOnly()
```

이 메서드들은 사람 정보에만 사용되는 규칙이 아니다.

예를 들면:

```text
requireText
→ 사람 이름, 공사명, 업체명, 현장명

validateLength
→ 이름, 주소, 계약 번호, 공사명

validateLettersOnly
→ 사람 이름 등

validateDigitsOnly
→ 전화번호, 계좌번호, 사업자 번호
```

따라서 `PersonValidator` 안에 중복해서 작성하지 않고 공통 클래스로 분리한 것은 적절하다.

의존 관계도 올바르다.

```text
PersonValidator
 ├─ PersonConfig
 └─ CommonValidator
```

반대로 `CommonValidator`가 `PersonConfig`를 알지 못한다는 점이 중요하다.

```text
CommonValidator
→ 어떻게 검사할지를 안다.

PersonValidator
→ 사람에게 어떤 검사를 적용할지를 안다.

PersonConfig
→ 사람에게 적용되는 기준값을 가진다.
```

역할이 명확하게 분리되어 있다.

---

## 3.3 PersonConfig가 실제 설정 클래스 역할을 하기 시작했다

`PersonConfig`에는 다음과 같은 값이 정의되었다.

```java
NAME_MIN_LENGTH
NAME_MAX_LENGTH

PHONE_LENGTH
PHONE_PREFIX

MALE_GENDER_ID
FEMALE_GENDER_ID
VALID_GENDER_IDS

ADDRESS_MIN_LENGTH
ADDRESS_MAX_LENGTH

VALID_BANK_NAMES

ACCOUNT_NUMBER_MIN_LENGTH
ACCOUNT_NUMBER_MAX_LENGTH
```

이로 인해 Validator 안에서 숫자나 문자열을 직접 작성하지 않아도 된다.

좋지 않은 방식:

```java
if (name.length() < 2 || name.length() > 5)
```

현재 방식:

```java
if (name.length() < PersonConfig.NAME_MIN_LENGTH
        || name.length() > PersonConfig.NAME_MAX_LENGTH)
```

이제 이름 길이 기준을 변경하려면 `PersonValidator`를 수정하지 않고 `PersonConfig`만 수정하면 된다.

이는 다음 두 가지를 분리한 것이다.

```text
규칙을 적용하는 코드
vs
규칙에 사용되는 기준값
```

설정 클래스의 사용 목적을 제대로 이해하고 적용하고 있다.

---

## 3.4 Set을 이용한 허용값 검사가 도입되었다

성별 코드 검사는 다음 구조다.

```java
if (!PersonConfig.VALID_GENDER_IDS.contains(genderId)) {
    throw new IllegalArgumentException(
            "올바르지 않은 성별 코드입니다."
    );
}
```

`VALID_GENDER_IDS`는 다음과 같다.

```java
Set.of(MALE_GENDER_ID, FEMALE_GENDER_ID)
```

따라서 실제 의미는 다음과 같다.

```text
허용 성별 코드 = {1, 2}

입력된 성별 코드가
이 집합에 포함되지 않으면 오류
```

기존처럼 다음 조건을 길게 작성하지 않아도 된다.

```java
genderId != 1 && genderId != 2
```

은행명도 같은 방식으로 허용 목록을 관리하기 시작했다.

```java
Set<String> VALID_BANK_NAMES
```

이것은 단순 문법 학습을 넘어, 허용값 목록을 코드 구조에 적용했다는 점에서 좋은 발전이다.

## 3.5 전체 사람 검증 메서드가 만들어졌다

다음 메서드가 추가되었다.

```java
public static void validatePerson(
        String name,
        String phone,
        int genderId,
        String address,
        String bank,
        String accountNumber
)
```

내부에서는 다음 순서로 각 검증 메서드를 호출한다.

```text
validateName
validatePhone
validateGenderId
validateAddress
validateBank
validateAccountNumber
```

이 구조의 장점은 Service에서 검증 세부사항을 알 필요가 없다는 것이다.

Service는 다음과 같이 호출할 수 있다.

```java
PersonValidator.validatePerson(
        name,
        phone,
        genderId,
        address,
        bank,
        accountNumber
);
```

그리고 검증이 모두 통과하면 저장 단계로 이동한다.

```text
PersonRegistrationService
  ↓
PersonValidator.validatePerson()
  ↓
PersonRepository.save()
```

이는 사람 등록 흐름을 구성할 준비가 거의 완료되었다는 의미다.

# 4. 현재 코드에서 수정할 부분

## 4.1 유틸리티 클래스에 final을 붙이는 것이 좋다

현재 클래스 선언은 다음과 같다.

```java
public class CommonValidator
public class PersonValidator
public class PersonConfig
```

이 클래스들은 다음 특징이 있다.

```text
생성자 private
모든 메서드 또는 값 static
객체 생성 목적 없음
상속 목적 없음
```

따라서 다음처럼 선언하는 것이 더 명확하다.

```java
public final class CommonValidator
public final class PersonValidator
public final class PersonConfig
```

`final`이 없어도 현재 기능은 작동한다.

다만 `final`을 붙이면 다음 의도가 코드에 드러난다.

> 이 클래스는 객체 생성이나 상속을 위한 클래스가 아니라 정적 기능과 설정을 제공하는 클래스다.

우선순위는 높지 않지만 간단히 개선할 수 있다.

---

## 4.2 validateLength는 단독 호출 시 null에 취약하다

현재 `validateLength()`는 바로 다음 코드를 실행한다.

```java
value.length()
```

따라서 누군가 다음처럼 호출하면:

```java
CommonValidator.validateLength(
        null,
        2,
        5,
        "이름"
);
```

`IllegalArgumentException`이 아니라 `NullPointerException`이 발생한다.

현재 `PersonValidator`에서는 먼저 `requireText()`를 호출하기 때문에 실제 흐름에는 문제가 없다.

```text
requireText
  ↓
validateLength
```

따라서 지금 당장 오류가 발생하는 구조는 아니다.

다만 `CommonValidator`가 재사용되기 시작하면 각 메서드의 호출 순서를 개발자가 반드시 기억해야 한다.

현재 단계에서는 다음 두 방향 중 하나를 선택할 수 있다.

### 현재 구조 유지

```text
requireText를 먼저 호출한다는 규칙을 유지
```

장점:

* 메서드가 단순하다.
* 중복 검사를 하지 않는다.

### validateLength 내부에서도 null 방어

```java
if (value == null) {
    throw new IllegalArgumentException(
            fieldName + "은(는) null일 수 없습니다."
    );
}
```

장점:

* 메서드를 단독으로 호출해도 안전하다.

지금은 현재 구조를 유지해도 충분하다. 대신 `CommonValidator` 사용 규칙을 알고 있어야 한다.

## 4.3 전화번호 오류 메시지에 공백이 빠져 있다

현재 코드는 다음과 같다.

```java
"전화번호는"
        + PersonConfig.PHONE_PREFIX
        + "으로 시작해야 합니다."
```

실제 출력은 다음과 같다.

```text
전화번호는010으로 시작해야 합니다.
```

다음처럼 공백을 추가하는 것이 좋다.

```java
"휴대폰 번호는 "
        + PersonConfig.PHONE_PREFIX
        + "으로 시작해야 합니다."
```

결과:

```text
휴대폰 번호는 010으로 시작해야 합니다.
```

또한 앞에서는 필드명을 `"휴대폰 번호"`로 사용하고, 여기서는 `"전화번호"`를 사용하고 있다.

하나로 통일하는 것이 좋다.

추천:

```text
휴대폰 번호
```

## 4.4 VALID_BANK_NAMES는 검증과 표준화 기준을 함께 검토해야 한다

현재 허용된 은행명은 다음 형태다.

```text
농협
국민
신한
우리
하나
기업
우체국
카카오
경남
```

이 방식은 사용자가 정확히 이 값 중 하나를 입력하면 잘 동작한다.

하지만 다음 값들은 현재 실패한다.

```text
NH농협
농협은행
KB국민은행
국민은행
IBK기업은행
카카오뱅크
경남은행
```

따라서 은행 입력 흐름을 명확하게 정해야 한다.

추천 흐름:

```text
사용자 입력
  ↓
PersonNormalizer.normalizeBank()
  ↓
별칭을 표준 은행명으로 변환
  ↓
PersonValidator.validateBank()
```

예:

```text
농협
NH농협
농협은행
       ↓
모두 "농협"으로 표준화
```

현재 `normalizeBank()`는 공백 제거만 수행한다.

```java
return removeAllWhitespace(bank);
```

따라서 별칭 변환은 아직 이루어지지 않는다.

현재 단계에서는 은행명을 직접 선택 번호로 받는 방법도 좋다.

```text
1. 농협
2. 국민
3. 신한
4. 우리
```

사용자가 자유롭게 문자를 입력하지 않고 메뉴에서 선택하면 오타와 별칭 문제가 줄어든다.

향후에는 다음 구조가 더 적절하다.

```text
bank 테이블
bank_alias 테이블 또는 별칭 Map
```

그러나 지금 당장 데이터베이스 구조를 확장할 필요는 없다.

## 4.5 계좌번호 최대 길이 30자는 다시 확인하는 것이 좋다

현재 설정은 다음과 같다.

```java
ACCOUNT_NUMBER_MIN_LENGTH = 10;
ACCOUNT_NUMBER_MAX_LENGTH = 30;
```

기능적으로 문제는 없다.

그러나 30자는 실제 계좌번호 기준이라기보다 상당히 넓은 범위다.

지금 단계에서는 잘못된 입력을 지나치게 엄격히 차단하지 않기 위해 넓게 설정한 것으로 볼 수 있다.

따라서 현재 값은 임시 기준으로 사용할 수 있다.

다만 다음과 같은 주석을 남기는 것이 좋다.

```java
// 은행별 계좌번호 길이 확인 후 범위 재조정
public static final int ACCOUNT_NUMBER_MIN_LENGTH = 10;
public static final int ACCOUNT_NUMBER_MAX_LENGTH = 30;
```

또는 은행별 규칙을 적용하기 전까지는 현재처럼 범위 검사만 사용하는 것이 현실적이다.

## 4.6 이름 검증은 영문과 한자를 허용한다

`validateLettersOnly()`는 다음 메서드를 사용한다.

```java
Character.isLetter(character)
```

따라서 다음은 모두 문자로 인정된다.

```text
홍길동
Hong
山田
```

반면 숫자, 하이픈, 특수문자는 거부한다.

```text
홍길동1
김-철수
홍 길동
```

현재 이름 Normalizer가 모든 공백을 제거한다면 `"홍 길동"`은 `"홍길동"`으로 변환된 뒤 통과한다.

이 설계는 현재 프로젝트에 적절하다.

다만 외국인 근로자를 등록할 가능성이 있다면 다음 이름도 고려할 수 있다.

```text
Jean-Pierre
Abdul Rahman
```

현재 규칙에서는 하이픈과 이름 내부 공백이 허용되지 않는다.

지금 당장 변경할 필요는 없지만, 향후 외국인 등록 정책을 정할 때 다시 검토해야 한다.

## 4.7 validatePerson의 매개변수가 많아지기 시작했다

현재 메서드는 6개의 매개변수를 받는다.

```java
validatePerson(
        name,
        phone,
        genderId,
        address,
        bank,
        accountNumber
)
```

현재는 충분히 읽을 수 있다.

하지만 사람 속성이 추가되면 다음처럼 길어질 수 있다.

```text
birthDate
employmentType
status
organizationId
positionId
hireDate
retirementDate
```

이때는 매개변수 순서를 잘못 전달할 가능성이 커진다.

최종적으로는 `PersonCreate` 객체를 받는 방식이 더 적합하다.

```java
public static void validate(PersonCreate person) {
    validateName(person.getName());
    validatePhone(person.getPhone());
    validateGenderId(person.getGenderId());
    validateAddress(person.getAddress());
    validateBank(person.getBank());
    validateAccountNumber(person.getAccountNumber());
}
```

그러면 Service는 다음처럼 호출한다.

```java
PersonValidator.validate(personCreate);
```

그러나 현재는 `PersonCreate`의 getter와 생성 흐름을 확정하는 단계이므로, 지금 작성한 6개 매개변수 방식도 잘못된 것은 아니다.

다음 Service 작성 단계에서 객체 전달 방식으로 전환하는 것을 추천한다.

# 5. 문서와 실제 프로젝트 상태의 차이

README에는 아직 다음 항목들이 개발 예정으로 표시되어 있다.

```text
SQLite 연결
Repository
Service
Person 등록
Person 조회

Person 삭제
CSV Import
```

하지만 실제 프로젝트에는 이미 `database`, `normalizer`, `validator`, `PersonConfig` 등이 추가되어 있다.

따라서 README의 프로젝트 구조와 현재 구현 상태가 실제 코드보다 뒤처져 있다.

또한 README 상단의 진행 메모에는 다음과 같은 내용이 남아 있다.

```text
다음 commit 할 것
PersonValidator 작성
```

이번 커밋에서 `PersonValidator`의 주요 검증 메서드는 대부분 작성되었으므로 다음처럼 갱신하는 것이 좋다.

```text
1. PersonCreate 모델 확인 완료
2. PersonNormalizer 작성 완료
3. PersonValidator 1차 작성 완료
4. PersonRepository 저장 메서드 작성 예정
5. PersonRegistrationService 작성 예정
6. PersonInputReader 작성 예정
```

README를 완벽하게 매 커밋마다 수정할 필요는 없다.

다만 다음 기능 단계로 넘어가기 전에 한 번 갱신하면 현재 위치를 잃지 않는 데 도움이 된다.

# 6. Git 관리 평가

## 잘된 점

이번 푸시는 정상적으로 완료되었다.

```text
bb7641a..df8b2db
main → main
```

로컬 `main` 브랜치가 원격 `origin/main`을 추적하도록 설정되어 있다.

```text
branch 'main' set up to track 'origin/main'
```

따라서 앞으로는 보통 다음 명령만 사용해도 된다.

```powershell
git push
```

매번 다음 명령을 입력할 필요는 없다.

```powershell
git push -u origin main
```

`-u`는 최초 연결이나 추적 브랜치를 다시 지정할 때 주로 사용한다.

---

## 커밋 메시지 개선 가능성

현재 메시지는 다음과 같다.

```text
PersonValidator Edit
```

무엇을 수정했는지는 대략 알 수 있지만, 이번 변경 범위는 Validator 하나보다 넓다.

실제로는 다음이 함께 추가되었다.

```text
PersonConfig 추가
CommonValidator 추가
PersonValidator 구현
은행·성별 허용 목록 추가
전화번호·주소·계좌번호 검증 추가
```

따라서 다음과 같은 메시지가 더 잘 어울린다.

```text
feat: add person validation rules and common validators
```

또는 현재 학습 스타일에 맞춰 조금 더 구체적으로:

```text
feat: implement PersonValidator and PersonConfig
```

한국어도 문제없다.

```text
feat: 사람 정보 검증기와 공통 검증 규칙 추가
```

현재 커밋 메시지가 잘못된 것은 아니다.

다만 나중에 이력을 볼 때 변경 목적을 더 빠르게 알 수 있도록 `feat`, `fix`, `refactor`, `docs` 같은 접두어를 사용하는 것이 도움이 된다.

# 7. 현재 아키텍처 평가

# 8. 다음 개발 순서 제안

README에 기록된 방향과 현재 코드 상태를 종합하면 다음 순서가 가장 자연스럽다.

## 1단계: 현재 Validator 마무리

작은 수정만 진행한다.

```text
전화번호 메시지 공백 수정
유틸리티 클래스 final 적용
은행명 표준화 정책 결정
PersonConfig 주석 정리
```

여기에 너무 오래 머물 필요는 없다.

---

## 2단계: PersonCreate 최종 확인

다음 필드와 생성자가 현재 요구사항에 맞는지 확인한다.

```java
String name
String phone
int genderId
String address
String bank
String accountNumber
```

특히 다음을 확인한다.

```text
모든 필드가 필수인가?
주소는 필수인가?
은행과 계좌번호는 함께 필수인가?
은행 정보가 없는 사람도 등록할 수 있는가?
```

예를 들어 일용 근로자를 먼저 이름과 전화번호만 등록하고, 나중에 계좌번호를 받을 가능성이 있다면 은행과 계좌번호는 선택값이 될 수 있다.

이 정책은 Validator 작성 전에 확정될 필요가 있다.

---

## 3단계: PersonRepository 작성

최소 기능은 사람 한 명을 데이터베이스에 저장하는 것이다.

```java
public long save(PersonCreate person)
```

Repository가 담당할 일:

```text
SQL 작성
PreparedStatement 값 연결
INSERT 실행
생성된 person_id 반환
SQLException 처리
```

Repository는 다음 일을 하면 안 된다.

```text
사용자 입력
공백 제거
이름 길이 검사
화면 출력
```

---

## 4단계: PersonRegistrationService 작성

Service의 예상 흐름:

```text
정규화된 데이터 받기
  ↓
PersonValidator로 검증
  ↓
PersonCreate 생성 또는 전달받기
  ↓
PersonRepository.save()
  ↓
등록 결과 반환
```

예상 형태:

```java
public long register(PersonCreate person) {
    PersonValidator.validate(person);
    return personRepository.save(person);
}
```

정규화를 UI 전에 할지 Service 안에서 할지는 다음 단계에서 확정하면 된다.

추천 흐름은 다음과 같다.

```text
UI
→ 원본 문자열 입력

Service
→ Normalizer
→ Validator
→ PersonCreate
→ Repository
```

이렇게 하면 CSV 등록과 수동 등록이 같은 Service를 사용할 수 있다.

---

## 5단계: PersonInputReader 작성

UI에서는 다음 역할만 담당한다.

```text
입력 안내문 출력
Scanner로 값 받기
Service 호출
예외 메시지 출력
재입력 여부 처리
```

UI가 다음 코드를 직접 반복해서 호출하지 않는 것이 좋다.

```java
normalizeName()
validateName()
normalizePhone()
validatePhone()
```

이 로직은 Service에서 한 흐름으로 묶는 것이 수동 입력과 CSV 입력의 중복을 줄이는 데 유리하다.

---

## 6단계: 사람 한 명 등록 완성

다음 흐름이 실제로 작동하는 것을 먼저 목표로 한다.

```text
사람 등록 메뉴 선택
  ↓
이름 입력
  ↓
전화번호 입력
  ↓
성별 선택
  ↓
주소 입력
  ↓
은행 입력
  ↓
계좌번호 입력
  ↓
정규화
  ↓
검증
  ↓
PersonCreate 생성
  ↓
SQLite 저장
  ↓

```

이 기능 하나가 완전히 작동한 후 조회 기능으로 넘어가는 것이 좋다.

# 9. 최종 평가

현재 프로젝트는 겉으로 보이는 기능 수는 아직 적지만, 내부 구조는 상당히 안정적으로 발전하고 있다.

특히 이번 작업에서 중요한 것은 검증 코드 몇 줄을 작성한 것이 아니다.

다음 개념을 실제 코드로 구현했다는 점이 더 중요하다.

```text
공통 규칙과 객체별 규칙의 분리
설정값과 실행 코드의 분리
표준화와 검증의 분리
허용값 목록을 Set으로 관리
검증 실패를 예외로 전달
여러 개의 세부 검증을 하나의 흐름으로 조합
```

이는 단순히 자바 문법을 따라 작성한 수준을 넘어, 객체지향 설계와 계층 분리를 실제 프로젝트에 적용하기 시작한 단계다.

## 현재 종합 평가

```text
프로젝트 방향          매우 좋음
역할 분리              매우 좋음
코드 가독성            좋음
검증 구조              좋음
설정 관리              좋음
데이터베이스 연결      진행 필요
Service 계층           진행 필요
테스트 코드            아직 없음
문서 최신화            필요
```

현재 가장 중요한 판단은 새로운 검증 기능을 계속 추가하는 것이 아니다.

이제 Validator는 사람 등록을 시작할 수 있을 정도로 만들어졌다.

다음 핵심 단계는 다음과 같다.

```text
PersonCreate 확인
  ↓
PersonRepository.save()
  ↓
PersonRegistrationService
  ↓
PersonInputReader
  ↓
실제 한 사람 등록 성공
```

## 결론

이번 커밋은 프로젝트에서 의미가 큰 커밋이다.

이전까지는 프로그램의 메뉴와 뼈대를 만들었다면, 이번에는 실제 데이터가 어떤 과정을 거쳐 안전한 객체가 되는지를 정의하기 시작했다.

현재 설계 방향을 유지하면서 사람 한 명 등록 기능을 끝까지 연결하는 것이 가장 좋은 다음 목표다.
