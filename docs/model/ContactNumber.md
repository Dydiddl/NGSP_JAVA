# ContactNumber

## 1. 목적

`ContactNumber`는 `Person`과 연락할 수 있는 전화번호 정보를 표현한다.

`Person`은 업무상 특정 사람을 식별하고 다시 연락할 수 있도록 관리하는 최소 단위이며, 최소 하나 이상의 `ContactNumber`를 가져야 한다.

한 사람이 여러 개의 전화번호를 가질 수 있으므로 `Person`과 `ContactNumber`는 1:N 관계를 가진다.

예:

```text
Person
├─ displayName: "김 주무관"
└─ contactNumbers
   ├─ MOBILE   / 010-1234-5678
   └─ LANDLINE / 055-123-4567
```

---

## 2. ContactNumber의 기본 정보

초기 구조는 다음과 같이 정의한다.

```text
ContactNumber
├─ number
└─ type
```

### number

실제 전화번호를 나타낸다.

예:

```text
010-1234-5678
055-123-4567
02-1234-5678
070-1234-5678
```

전화번호는 입력된 표현을 그대로 검증하지 않고 정규화 과정을 거친 후 검증한다.

### type

전화번호 체계상 번호의 종류를 나타낸다.

구체적인 enum 값은 대한민국 전화번호 체계를 조사한 후 확정한다.

예상되는 대표적인 분류는 다음과 같다.

```text
MOBILE
LANDLINE
INTERNET_PHONE
기타 필요한 전화번호 종류
```

개인용, 업무용 등의 **사용 목적은 관리하지 않는다.**

현재 업무 흐름에서 필요한 것은 해당 사람에게 연락할 수 있는 번호와 번호의 종류이며, 개인용/업무용 구분은 실제로 기록하거나 관리할 필요가 확인되지 않았다.

따라서 현재 필요하지 않은 분류를 추가하여 모델을 복잡하게 만들지 않는다.

---

## 3. 한 Person은 여러 전화번호를 가질 수 있다

한 사람은 여러 개의 연락 가능한 전화번호를 가질 수 있다.

예:

```text
Person: 김철수

ContactNumber
├─ MOBILE         / 010-1111-2222
├─ LANDLINE       / 055-123-4567
└─ INTERNET_PHONE / 070-1234-5678
```

따라서 `Person` 내부에서 단일 `phone` 문자열로 관리하지 않고 여러 `ContactNumber`를 관리할 수 있는 구조를 사용한다.

다만 `Person`은 업무상 다시 연락할 수 있는 사람을 관리하기 위한 객체이므로 **최소 하나 이상의 ContactNumber가 반드시 존재해야 한다.**

---

## 4. 전화번호 변경

등록된 전화번호 자체가 변경된 경우 현재 요구사항에서는 일반적인 **수정(update)** 으로 취급한다.

예:

```text
기존
010-1111-2222

        ↓ 수정

신규
010-3333-4444
```

현재 프로그램에서는 이전 전화번호의 변경 이력을 보존해야 할 업무상 요구사항이 없다.

따라서 다음과 같은 별도 기능은 현재 구현하지 않는다.

```text
기존 번호 삭제
→ 변경 이력 저장
→ 새로운 번호 등록
```

사용자 관점에서는 기존 `ContactNumber`의 번호를 새로운 번호로 수정하는 것으로 처리한다.

향후 과거 연락처 이력을 보존해야 할 실제 업무 요구사항이 발생한다면 그때 별도의 이력 관리 구조를 검토한다.

---

## 5. 대한민국 전화번호 체계를 기준으로 한다

현재 프로그램의 업무 범위에서는 대한민국 전화번호를 대상으로 한다.

따라서 `ContactNumber`의 첫 번째 완성 목표는 **대한민국에서 사용하는 전화번호 체계를 조사하고 유효한 국내 전화번호를 정확하게 정규화·분류·검증할 수 있는 구조를 만드는 것**이다.

단순히 `010` 휴대전화만 검증하지 않는다.

다음과 같은 번호 체계를 조사하여 구현 범위를 확정한다.

```text
- 휴대전화 번호
- 서울 및 각 지역의 지역번호
- 인터넷 전화
- 기타 실제 업무 연락처로 사용 가능한 국내 전화번호 체계
```

지역번호는 정해진 전화번호 체계이므로 전체 목록을 확인하여 검증에 사용한다.

지역번호와 같이 전화번호 체계 자체에 의해 정해지는 값은 프로그램 운영 중 사용자가 임의로 변경하는 설정값과 구분한다.

따라서 이러한 값은 `PersonConfig` 같은 일반 프로그램 설정이 아니라 전화번호 도메인 규칙에 가까운 위치에서 관리한다.

---

## 6. 검증 목표

`ContactNumber`의 최종 목표는 단순한 문자열 보관이 아니라 **유효한 대한민국 전화번호만 ContactNumber 객체로 생성될 수 있도록 하는 것**이다.

따라서 최종적으로 대한민국 전화번호 체계를 기준으로 가능한 한 완전한 검증을 구현한다.

검증에서는 최소한 다음 요소들을 고려한다.

```text
null / blank
전화번호 구성 문자
정규화 후 길이
접두번호
휴대전화 번호 체계
지역번호
지역번호에 따른 전체 번호 구조
인터넷 전화번호
그 밖의 실제 국내 전화번호 체계
```

다만 구현은 단계적으로 진행할 수 있다.

첫 번째 구현에서는 우선:

```text
- null 불가
- blank 불가
```

등 가장 기본적인 불변식부터 적용할 수 있다.

이후 대한민국 전화번호 체계를 조사하여 검증 규칙을 추가하고 최종적으로 완성된 `ContactNumber` 검증 체계를 만드는 것을 목표로 한다.

즉 **완전한 검증 자체를 미래 과제로 미루는 것이 아니라, 완전한 검증을 목표로 하되 구현 순서를 나누는 것**이다.

---

## 7. 정규화

전화번호 정규화에는 기존 `TextNormalizer`를 최대한 재사용한다.

현재 프로젝트에는 휴대전화 번호 입력을 처리하기 위한 전화번호 정규화 기능이 존재하므로 이를 검토하고 일반 전화번호에도 사용할 수 있도록 필요한 부분만 수정한다.

사용자는 같은 번호를 다음처럼 입력할 수 있다.

```text
010-1234-5678
010 1234 5678
01012345678
```

이 값들은 동일한 전화번호로 판단할 수 있어야 한다.

개념적인 처리 순서는 다음과 같다.

```text
사용자 입력
010-1234-5678

        ↓ TextNormalizer

01012345678

        ↓ ContactNumber 검증

유효한 대한민국 휴대전화 번호

        ↓

ContactNumber 생성
```

정규화와 검증의 책임은 구분한다.

```text
TextNormalizer
= 입력 표현을 비교·검증 가능한 형태로 정규화

ContactNumber
= 정규화된 값이 전화번호 도메인 규칙을 만족하는지 보장
```

기존 코드로 해결할 수 있는 기능을 중복 구현하지 않는다.

---

## 8. 번호 종류 판별

전화번호의 종류는 가능한 경우 번호 자체의 규칙을 이용하여 판별할 수 있도록 설계한다.

예:

```text
010...
→ MOBILE

지역번호...
→ LANDLINE

070...
→ INTERNET_PHONE
```

따라서 사용자가 번호와 번호 종류를 서로 독립적으로 입력하여 다음과 같은 모순을 만들지 않도록 하는 방향을 우선 검토한다.

```text
number = 01012345678
type   = LANDLINE
```

번호 자체로 종류를 확실하게 판단할 수 있다면 `type`을 사용자에게 별도로 입력받기보다 `ContactNumber`가 번호를 분석하여 결정하는 방식이 더 안전하다.

다만 실제 대한민국 전화번호 체계를 조사한 결과 번호만으로 종류를 확정할 수 없는 사례가 존재한다면 해당 경우를 별도로 설계한다.

---

## 9. 대표 연락처

현재는 대표 연락처 기능을 구현하지 않는다.

Person을 검색하면 해당 Person이 가지고 있는 모든 연락처를 보여주는 것을 기본 동작으로 한다.

예:

```text
김철수

[MOBILE]
010-1111-2222

[LANDLINE]
055-123-4567
```

현재 사용 방식에서는 사용자가 검색 결과를 확인한 뒤 필요한 전화번호를 직접 선택하여 사용한다.

따라서 특정 번호 하나를 대표 연락처로 지정할 필요가 없다.

향후 프로그램 자체에서 다음과 같은 기능이 추가될 경우 대표 연락처 개념을 다시 검토한다.

```text
Person 검색
→ 프로그램에서 바로 전화 걸기
```

이처럼 하나의 연락처를 자동 선택해야 하는 실제 요구사항이 발생했을 때 대표 연락처 기능을 추가한다.

---

## 10. 현재 구현하지 않을 사항

현재 요구사항에서 필요성이 확인되지 않은 다음 기능은 구현하지 않는다.

- 개인용 / 업무용 전화번호 구분
- 대표 연락처 지정
- 전화번호 변경 이력
- 삭제된 전화번호 이력
- 국제전화번호 및 국가별 전화번호 체계

대한민국 전화번호 체계와 관련된 다음 사항은 구현 대상에 포함한다.

- 국내 휴대전화 번호 검증
- 국내 지역번호 전체 목록 확인 및 검증
- 일반 유선전화 번호 검증
- 인터넷 전화번호 검증
- 실제 업무 연락처로 사용될 수 있는 기타 국내 전화번호 체계 조사
- 번호 종류 판별

## 11. 설계 원칙

`ContactNumber`는 다음 원칙을 따른다.

### 1. 실제 업무에 필요한 정보만 관리한다

현재 사용하지 않는 개인용/업무용 등의 분류는 미래 가능성만으로 추가하지 않는다.

### 2. 전화번호 자체의 규칙은 ContactNumber가 보장한다

`ContactNumber` 객체가 존재한다면 프로그램에서는 해당 값이 유효한 대한민국 전화번호라고 신뢰할 수 있는 것을 최종 목표로 한다.

### 3. 정규화와 검증을 분리한다

기존 `TextNormalizer`를 재사용하여 입력 형식을 정리하고 `ContactNumber`가 전화번호 도메인 규칙을 검증한다.

### 4. 유한하고 안정적인 도메인 규칙은 명시적으로 관리한다

지역번호와 같이 대한민국 전화번호 체계에 의해 정해진 값은 조사하여 명시적으로 관리하고 검증에 사용한다.

### 5. 실제 요구사항이 없는 기능은 추가하지 않는다

변경 이력, 대표 연락처, 개인/업무 구분 등은 실제 필요성이 발생할 때 추가한다.

### 6. 구현은 단계적으로 하되 목표 수준을 낮추지 않는다

초기에는 `null`, `blank` 등의 기본 검증부터 시작할 수 있지만 최종적으로는 대한민국 전화번호 체계를 정확하게 반영하는 완성도 높은 검증을 목표로 한다.

---

## 12. 현재 모델

```text
Person
├─ id
├─ displayName
├─ contactNumbers  // 1개 이상
├─ name?
└─ email?

        │
        │ 1:N
        ▼

ContactNumber
├─ number
└─ type
```

`ContactNumber`의 `type`은 대한민국 전화번호 체계를 조사한 뒤 정확한 분류를 확정한다.

가능하면 `number`를 통해 `type`을 자동 판별하여 번호와 타입 사이의 모순된 상태가 만들어지지 않도록 한다.
